# Quiz Web App

Quiz Web App — веб-платформа для проведения квизов в реальном времени. Организатор создаёт квиз, добавляет вопросы, запускает игровую сессию и передаёт участникам код комнаты. Участники подключаются, отвечают на вопросы синхронно, а по завершении игры получают итоговый лидерборд.

## Возможности

- Регистрация и вход с ролями `organizer` и `participant`.
- Создание, редактирование и удаление квизов.
- Текстовые вопросы и вопросы с изображениями.
- Одиночный и множественный выбор ответа.
- Настройка баллов, времени на вопрос, перемешивания и режима запуска.
- Игровые комнаты с уникальным кодом подключения.
- Обновление вопросов, участников и рейтинга через WebSocket.
- Ручной и автоматический режим прохождения.
- Итоговые результаты и история проведённых или пройденных квизов.

## Роли и доступ

### Организатор

Организатор может создавать и редактировать только собственные квизы, запускать сессии по своим квизам, запускать вопросы и завершать сессию. Он видит код комнаты, список подключившихся игроков, текущий лидерборд и историю проведённых игр.

### Участник

Участник подключается к сессии по коду комнаты, отвечает на активные вопросы, видит свой текущий результат и открывает историю пройденных игр. Отправить ответ можно только после подключения к сессии и только один раз для каждого вопроса.

## Пользовательский сценарий

1. Организатор регистрируется с ролью `organizer`.
2. Создаёт квиз и добавляет вопросы.
3. Настраивает режим запуска: `manual` или `automatic`.
4. Запускает игровую сессию и получает код комнаты.
5. Участники регистрируются с ролью `participant`, вводят код и подключаются.
6. Организатор запускает вопрос либо автоматический сценарий.
7. Сервер рассылает состояние сессии всем подключённым клиентам.
8. Участники отправляют ответы через WebSocket.
9. Сервер подсчитывает баллы и обновляет лидерборд.
10. После последнего вопроса или команды организатора сессия завершается, а финальный результат сохраняется.

## Модель данных

| Сущность | Назначение | Ключевые поля и ограничения |
| --- | --- | --- |
| `users` | Учётные записи | Уникальный `email`, роль, отображаемое имя, хеш пароля |
| `quizzes` | Квиз организатора | Владелец, название, описание, статус, JSON-настройки |
| `questions` | Вопросы квиза | Тип, режим выбора, текст, изображение, баллы, время, позиция; уникальна пара `quiz_id + position` |
| `answers` | Варианты ответа | Текст, правильность и позиция |
| `sessions` | Игровые сессии | Квиз, организатор, уникальный `room_code`, статус, время завершения, финальный JSON-результат |
| `session_participants` | Участники сессии | Уникальна пара `session_id + user_id` |
| `question_events` | Фактические запуски вопросов | Сессия, вопрос, статус, начало и завершение; в одной сессии может быть только один активный вопрос |
| `question_responses` | Ответы игрока | Выбранные варианты, текстовый ответ, начисленные баллы; один ответ участника на один запуск вопроса |

Удаление квиза, сессии или вопроса каскадно удаляет связанные сущности. Ограничения PostgreSQL защищают от повторного подключения пользователя к одной сессии, повторного ответа на вопрос и одновременного наличия нескольких активных вопросов в одной сессии.

## Валидация квизов

Для каждого вопроса система проверяет:

- текст вопроса обязателен;
- вопрос с изображением должен содержать корректный `http` или `https` URL;
- текстовый вопрос не может содержать URL изображения;
- доступны от 2 до 20 вариантов ответа;
- для `single` должен быть ровно один правильный вариант;
- для `multiple` должно быть не менее двух правильных вариантов;
- баллы находятся в диапазоне от 1 до 1000;
- продолжительность вопроса — от 5 до 3600 секунд.

Настройки квиза включают время по умолчанию, перемешивание вопросов и ответов, отображение правильных ответов, режим подсчёта и режим запуска.

## Real-time протокол

Клиент подключается к сессии по WebSocket:

```text
ws://localhost:8000/ws/sessions/{room_code}?token={access_token}
```

Сервер проверяет JWT, существование комнаты и право пользователя подключаться к ней. Организатор подключается как владелец сессии, а участник — только после успешного входа в комнату.

После подключения сервер отправляет состояние `session.updated`:

```json
{
  "type": "session.updated",
  "scoreboard": {
    "session_id": "...",
    "status": "waiting | active | ended",
    "entries": [{"participant_id": "...", "display_name": "Ada", "score": 10, "rank": 1}],
    "winner_ids": ["..."]
  },
  "current_question": null
}
```

При наличии активного вопроса `current_question` содержит его идентификатор, текст, режим выбора, время завершения, URL изображения и публичные варианты ответа. Признак правильности ответа участникам не передаётся.

Поддерживаются следующие команды. Каждая команда должна содержать уникальный `request_id`.

| Команда | Кто отправляет | Назначение |
| --- | --- | --- |
| `question.start` | Организатор | Запускает указанный вопрос; опционально передаётся `duration_seconds` |
| `answer.submit` | Участник | Сохраняет выбранные варианты и/или текстовый ответ |
| `session.end` | Организатор | Завершает игровую сессию |

После успешной обработки сервер отправляет инициатору `command.accepted`, затем рассылает всем клиентам актуальное `session.updated`. При ошибке или нарушении роли клиент получает `command.error`.

Отдельное событие `participants.updated` отправляется только организаторам после подключения участника.

## Автоматическое прохождение

При запуске FastAPI создаётся фоновая задача `automatic_playback_loop`. Она отслеживает вопросы, время которых истекло, переводит их в закрытое состояние и запускает следующий вопрос в автоматическом режиме. После последнего вопроса сессия завершается.

Переходы выполняются с блокировками строк PostgreSQL. Это предотвращает дублирование переходов, если приложение работает в нескольких процессах или фоновая проверка срабатывает одновременно.

## HTTP API

Swagger UI доступен после запуска по адресу [http://localhost:8000/docs](http://localhost:8000/docs).

| Метод | Маршрут | Доступ | Назначение |
| --- | --- | --- | --- |
| `GET` | `/health` | публичный | Проверка доступности API |
| `POST` | `/auth/register` | публичный | Регистрация пользователя |
| `POST` | `/auth/login` | публичный | Получение JWT access token |
| `GET` | `/users/me` | авторизованный | Данные текущего пользователя |
| `PATCH` | `/users/me` | авторизованный | Изменение отображаемого имени |
| `POST` | `/quizzes` | организатор | Создание квиза |
| `GET` | `/quizzes` | организатор | Список собственных квизов |
| `GET` | `/quizzes/{quiz_id}` | организатор-владелец | Получение квиза |
| `PATCH` | `/quizzes/{quiz_id}` | организатор-владелец | Редактирование квиза и настроек |
| `DELETE` | `/quizzes/{quiz_id}` | организатор-владелец | Удаление квиза |
| `POST` | `/quizzes/{quiz_id}/questions` | организатор-владелец | Добавление вопроса |
| `GET` | `/quizzes/{quiz_id}/questions` | организатор-владелец | Список вопросов |
| `PUT` | `/quizzes/{quiz_id}/questions/{question_id}` | организатор-владелец | Редактирование вопроса |
| `POST` | `/sessions` | организатор | Создание игровой сессии |
| `POST` | `/sessions/join` | участник | Подключение по коду комнаты |
| `GET` | `/sessions/{session_id}` | участник сессии или организатор | Контекст сессии |
| `GET` | `/sessions/{session_id}/result` | участник сессии или организатор | Итоговый результат |
| `GET` | `/sessions/history/conducted` | организатор | История проведённых сессий |
| `GET` | `/sessions/history/participated` | участник | История пройденных сессий |

Для списков квизов и истории поддерживается пагинация параметрами `limit` и `offset`. Значение `limit` находится в диапазоне от 1 до 100.

## Безопасность

- Пароли хешируются `scrypt` с уникальной солью, а сравнение хешей выполняется в constant-time режиме.
- Access token — JWT, подписанный HS256; в нём содержатся ID пользователя, роль, тип токена и срок действия.
- API и WebSocket проверяют действительность токена и роль пользователя.
- Операции над квизами ограничены их владельцем.
- Участник не может подключиться к WebSocket комнаты без предварительного присоединения к сессии.
- В production обязательно задайте уникальный `JWT_SECRET_KEY` длиной не менее 32 символов и ограничьте `CORS_ORIGINS` доверенными доменами.

## Конфигурация

Создайте локальные файлы окружения:

```bash
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

Параметры backend:

| Переменная | Назначение |
| --- | --- |
| `APP_NAME` | Название приложения FastAPI |
| `ENVIRONMENT` | Окружение выполнения |
| `DATABASE_URL` | Асинхронная строка подключения PostgreSQL |
| `JWT_SECRET_KEY` | Секрет подписи JWT, минимум 32 символа |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Время жизни access token в минутах |
| `CORS_ORIGINS` | Разрешённые origins, через запятую |

Параметр frontend:

| Переменная | Назначение |
| --- | --- |
| `VITE_API_URL` | Базовый URL FastAPI API |

Файл `backend/.env` не включается в Docker-образ. В Docker Compose PostgreSQL доступен только контейнерам и не публикует порт на хост.

## Быстрый запуск через Docker

```bash
docker compose up --build
```

Compose запускает:

- `db` — PostgreSQL 16 с постоянным volume `postgres_data`;
- `api` — применяет `alembic upgrade head`, затем запускает Uvicorn на порту `8000`;
- `frontend` — Vite-клиент на порту `5173`.

После запуска:

- приложение: [http://localhost:5173](http://localhost:5173);
- OpenAPI/Swagger: [http://localhost:8000/docs](http://localhost:8000/docs);
- health check: [http://localhost:8000/health](http://localhost:8000/health).

## Тестирование и проверки

Запуск backend-тестов:

```bash
cd backend
python -m pytest -q
```

Быстрая проверка точки входа backend:

```bash
cd backend
python -m py_compile app/main.py
```

Сборка frontend:

```bash
cd frontend
npm run build
```

Тесты покрывают регистрацию и авторизацию, безопасность токенов и паролей, CRUD квизов, валидацию вопросов, модель и миграции сессий, подключение участников, подсчёт баллов, историю игр, WebSocket-обработчик, автоматическое прохождение и защиту от конфликтов активных вопросов.

## Работа с миграциями

Применить миграции:

```bash
cd backend
alembic upgrade head
```

Создать новую миграцию после изменения ORM-моделей:

```bash
cd backend
alembic revision --autogenerate -m "describe change"
```

Перед добавлением миграции проверьте её вручную: автогенерация не всегда корректно определяет изменения ограничений, индексов и enum-полей.
